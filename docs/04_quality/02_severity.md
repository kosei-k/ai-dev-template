# Severity定義（Critical / Major / Minor）

> **これは雛形です。** `.claude/04_quality/02_severity.md` にコピーし、
> **「例」の節を自分のプロジェクトの具体例に書き換えてください。**
> ここが埋まっていないと `reviewer` は判断基準を持たず、精度が落ちます。

AIレビューの指摘は必ずこの3段階に分類する。**PASS/FAILゲートの信頼性はこの分類の
一貫性で決まる**ため、迷ったら本ファイルの具体例と判定基準に従う。

## 判定フロー

1. 「この欠陥が本番で出たら、**このプロジェクトにとって最悪のこと**が起きるか？」
   → YES なら **Critical**
2. 「仕様・規約への明確な違反、またはユーザー影響のあるバグか？」→ YES なら **Major**
3. それ以外（動作は正しいが品質・一貫性の問題）→ **Minor**

判断に迷う場合は `CLAUDE.md` の最重要原則に照らす。

> **プロジェクト固有: 最重要原則をここに書く。**
> 例）「正確性 > 見逃さないこと > 見た目 > 機能追加」
> この順序が Critical の判定根拠になる。

## Critical — このプロジェクトにとって最悪の欠陥

> **プロジェクト固有: 具体例を5〜10個書く。**
> 抽象論ではなく、実際のコードで起こりうる形で書くこと。
> 「〜のとき〜が〜になる」という具体性があるほど `reviewer` の精度が上がる。

例（金融監視システムの場合）:

- 取得失敗を「正常」として表示・判定する
- 閾値を超えているのに警告が出ない、または超えていないのに出る
- 設定の並び順が意味と矛盾していて、例外も出さずに静かに壊れる

例（ECサイトの場合）:

- 決済金額と請求金額が一致しない
- 他人の注文情報が見える
- 在庫を確保せずに注文を確定させる

## Major — 仕様違反・ユーザー影響のあるバグ・必須テストの欠落

例:

- 判定ロジックの変更にテストが追加されていない
- 機械検査で検出できるはずのものがすり抜けている
- 制約に反する依存パッケージの追加
- ドキュメントとコードの乖離を放置している

## Minor — 動作は正しいが保守性・一貫性の問題

例:

- コメント・docstring の陳腐化（挙動を正しく説明できていないが誤動作はしない）
- 命名の一貫性からの軽微な逸脱
- 体裁の問題

## PASS/FAIL判定

```
PASS = Critical 0件 かつ Major 0件
FAIL = Critical または Major が1件以上
```

Minorのみの場合は **PASS**（指摘は残すが修正必須ではない）。

コードから確認できない憶測（「〜かもしれない」）は指摘にしない。懸念として書きたい
場合はMinorではなく、レポート末尾の「質問・確認事項」に書く。

## plan-reviewer 向け: 要対応 / 任意

`plan-reviewer` が見るのは**まだ実装されていない計画**であり、Critical（本番障害）の
概念がそのまま当てはまらない。代わりに2段階で分類する。

### 要対応

- 異常系・エラー時の挙動が計画に書かれていない
- 判断の根拠（実績値・出典・比較検討）が書かれていない
- 既存の設計と矛盾する設計になっている
- 受け入れケースが計画書内に列挙されていない

### 任意

- 表現・体裁の改善
- 「あればなお良い」レベルの追加観点

```
PASS = 要対応 0件
FAIL = 要対応が1件以上
```

この判定は**非ゲート**（FAILでもCIは失敗しない。人間がApproveで最終判断する）。
