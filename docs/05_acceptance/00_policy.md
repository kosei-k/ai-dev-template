# 受け入れケースの体系

> **これは雛形です。** `.claude/05_acceptance/00_policy.md` にコピーし、
> プレフィックスを自分のモジュール構成に合わせてください。

## ID の形式

```
<モジュール>-AC-<3桁連番>      例: RULES-AC-001, WEB-AC-012
```

プレフィックスはモジュール単位。連番はプレフィックスごとに独立し、**欠番は許容する**
（削除したケースの番号を再利用しない。過去のPRやコミットとの対応が壊れるため）。

## テストとの紐づけ

**テストコード内のコメントとして ID を書く。**

```python
def test_threshold_boundary():
    # RULES-AC-002: 閾値ちょうどの値が正しく判定される
    ...
```

`docs_lint` が台帳とテストを**無条件に双方向突合**する。

- 台帳に載っているのにテストに出現しないID → エラー
- テストに出現するのに台帳に載っていないID → エラー

## 台帳への追加タイミング

**台帳への追加は、対応するテストと同じPRで行う。**

`docs_lint` にはStatus（todo/done）の概念が無く、**台帳に載っているIDは常にテストと
対応している前提**で検査する。したがって:

| フェーズ | やること |
|---|---|
| Plan PR | 計画書内の「受け入れケース」節に**列挙するだけ**。台帳には追加しない |
| 実装PR | テストを書き、**同じPRで**台帳に行を追加する |

Plan PRの時点で台帳に追加すると、テストがまだ存在しないため `docs_lint` が即座に
失敗する。またPlan PR承認から実装着手までの間に他のPRで番号が進むことがあるため、
**IDの確定は実装時**に行う。

## 優先度

| P | 意味 |
|---|---|
| P0 | 壊れたらこのプロジェクトの最重要原則に反する。必ずテストする |
| P1 | ユーザー影響がある。テストする |
| P2 | 品質・一貫性の問題。余裕があればテストする |

## 台帳の書式

`.claude/05_acceptance/01_scope.md` にモジュールごとの表として書く。

```markdown
## RULES（rules.py）

| ID | P | 受け入れ基準 | 検証手段 |
|---|---|---|---|
| RULES-AC-001 | P0 | 閾値ちょうどの値がwatch判定になる | pytest |
```

**受け入れ基準は「何がどうなれば合格か」を1行で書く。** 実装方法は書かない。
