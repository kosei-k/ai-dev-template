# 計画のテンプレート

> **これは雛形です。** `.claude/00_project/03_plan_template.md` にコピーし、
> プロジェクトに合わせて節を足し引きしてください。
> `plan-reviewer` はこのファイルを基準に「計画の抜け」を検出します。

> 目的は **実装前に仕様と異常系の合意を取り、手戻りをなくすこと**。
> 「うまくいったとき」しか書かれていない計画は不完全です。

`.claude/07_plans/NN_<slug>.md` として保存する。冒頭ヘッダ:

```markdown
# NN. <計画のタイトル>

- Status: planned
- Issue: #<Issue番号>
- PR: -
```

Status は `planned → in_progress`（実装PRを作業中）`→ done`（マージ完了、以後編集禁止）。

---

## 1. 背景・目的

なぜこの変更をするのか。解決する課題と、**完了時に得られる状態**。
「何を作るか」ではなく「何が困っていて、どうなれば終わりか」を書く。

## 2. 仕様

変更の中身を、実装ではなく**外から見た振る舞い**として書く。

- 入力（誰が・何を・どこから）
- 出力（何が・どこに・どんな形で）
- 判断が要る値がある場合は、**その根拠**（実績値・出典・比較検討）を必ず添える

## 3. 状態の一覧（ここを飛ばすと手戻りが出る）

**実装前に文章で確定させる。** 少なくとも次の4つは必ず埋める。

| 状態 | 表示・振る舞い |
|---|---|
| 正常 | |
| 処理中 | ユーザーに何が見えるか。**前の内容を消さない**のが原則 |
| 失敗 | 何が起きたか分かるか。**成功と見分けがつくか** |
| データが無い | 空白にしない。「無い」ことを明示する |

プロジェクト固有の状態があれば足す（部分的な失敗、権限がない、期限切れ、
容量超過、同時操作の衝突など）。

**特に確認する点:**

- 失敗を成功と混同させない設計になっているか
- 処理中に前の状態が消えないか（消えると失敗と区別できない）
- 取り返しのつかない操作（削除・送信・確定）の前に確認があるか

## 4. 技術設計

このプラン自体に技術設計を文章で書く。設計ドキュメント本体はPlan PRでは更新しない
（実装PRで、実装コードと同じPRで更新する）。

- 変更するモジュールと、その責務
- 外部への依存（API・ストレージ・依存パッケージ）が増えるか
- **後戻りが高くつく決定**が含まれる場合は、ADRを別途書く

## 5. 受け入れケース

`.claude/05_acceptance/00_policy.md` の体系（`<PREFIX>-AC-<3桁連番>`）に従って、
追加・変更するケースを下表に列挙する。

**台帳ファイルへは追加しない**（`docs_lint` がテスト未追加のIDを即座にエラーに
するため）。台帳への追加は対応するテストと同じ実装PRで行う。

| ID | P | 受け入れ基準 | 検証手段 |
|---|---|---|---|
| | | | |

境界値（両側）・値なし・条件の組み合わせの抜けを確認する。

## 6. 更新する資料

事前に列挙する。**プラン承認 = この範囲の更新の承認。**

- [ ] ADR（後戻りが高くつく決定・複数案の比較がある場合）
- [ ] README

### 実装PRで更新する（今は更新しない・実装時の申し送り）

- [ ] 設計ドキュメント
- [ ] 受け入れケース台帳（テストと同時）

## 7. DoD（完了の定義）

- [ ] `[project] check_command` が通る
- [ ] 受け入れケースが台帳に載り、対応するテストにIDコメントが入っている
- [ ] §6「実装PRで更新する」が実装PRで更新されている
- [ ] §3 の状態を実際に手で確認した

## 8. リスク・未確定事項

判断を要する点、後戻りが高くつく決定、中止条件があれば書く。
**「分かっていないこと」を正直に書く**のがこの節の価値。
