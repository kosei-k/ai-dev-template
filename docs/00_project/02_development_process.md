# 開発プロセス

> **これは雛形です。** `.claude/00_project/02_development_process.md` にコピーし、
> §2 のトリガー表を自分のプロジェクトに合わせて書き換えてください。

## §1 全体の流れ

```
Issue（人間が要件を書く）
    ↓ /plan <Issue番号>（トリガー表で必須の場合）
Plan PR（原則コード0行。AIが不明点を質問 → 人間が回答 → 人間がApprove）
    ↓
実装
    ↓ /pr
実装PR（reviewer / plan-reviewer / guard / CI）
    ↓ 人間がApprove
マージ
```

人間のタスクは3つに畳む: **要件を書く / 質問に答える / Plan PRと実装PRをApproveする。**

## §2 トリガー表

> **プロジェクト固有: 「変更種別」の行を自分のプロジェクトの語彙で書き換える。**
> 判断の重い変更ほどPlan PRを必須にする。

| 変更種別 | Plan PR | ADR | 受け入れケース |
|---|---|---|---|
| バグ修正 | 不要（実装PRに同梱） | なし | 仕様の欠落だった場合のみ追加 |
| リファクタ・保守 | 不要 | なし | なし |
| 表示・体裁の変更 | 不要 | なし | 挙動が変わる場合のみ |
| **新機能の追加** | **必須** | 場合による | ○ |
| **判断が要る値の変更** | **必須** | **必須** | ○ |
| **技術選定・依存追加・公開範囲の変更** | **必須** | **必須** | 対象外 |

判定に迷う場合（例: 「バグ修正」に見えて実は仕様が欠けていた）は、**Plan PR を作る側に倒す。**
やりすぎのコストより、手戻りのコストの方が高い。

## §3 Plan PR

`.claude/07_plans/NN_<slug>.md` を追加する PR。`03_plan_template.md` の形式に従う。
原則コード0行。**目的は実装前に仕様と異常系の合意を取り、手戻りをなくすこと。**

ブランチ名は `feature/plan-*` にする（この接頭辞で `plan-reviewer` が起動する）。

Plan PR承認後、プランの「更新する資料」に列挙したファイルの更新には**追加の承認を
求めない**（承認済みの範囲として扱う）。

## §4 実装PR

計画に基づき実装する。コード変更と同じPRで:

- 設計ドキュメントを更新
- **受け入れケース台帳に、追加したテストと対応する行を追加する**
  （Plan PRでは追加しない。テストと台帳は同じPRで揃える）
- READMEを必要なら更新

## §5 ゲート

| ゲート | 責任 | ブロッキング |
|---|---|---|
| `[project] check_command` | コード品質・カバレッジ・ドキュメント整合 | **ブロッキング** |
| `ai-review.yml`（reviewer→fixer） | 差分の欠陥検出・自動修正 | **ブロッキング**（`VERDICT: FAIL`で赤） |
| `guard.yml`（テスト弱体化検知） | fixerの暴走防止 | **ブロッキング**（BLOCK時） |
| `ai-review.yml`（plan-reviewer、Plan PRのみ） | 計画の抜け検出 | 非ゲート。人間が最終判断 |
| 人間のApprove | 要件・優先順位との整合 | **ブロッキング** |

## §6 ADR を書く条件

以下のいずれかに該当する決定は ADR にする（該当しない決定は、そのプランや実装PRの
説明に書けば足りる）:

1. **判断が要る値の変更**（根拠が消えると再現できなくなるもの）
2. **複数案を比較して選んだ決定**（後から「なぜこちらを選んだか」が要る）
3. **後から覆すと高くつく決定**（アーキテクチャ・技術選定・依存の追加・公開範囲）
4. **`CLAUDE.md` に新しい規則を追記することになる決定**

ADR は**書き換えず `Superseded by` で積む**。連番は既存の最大値+1、2桁ゼロ埋め。
